# Astra提案

> 先ほどの企画再提案の記録です。本文中の実装状況・コミット・作業ツリーへの言及は提案時点のものです。

方向転換に賛成です。現在の作品は、動く部分が増えても「誰の、どんな事故を防げるのか」が伝わりにくく、受賞を狙ううえで訴求が弱いと感じます。前回は、その価値の絞り込みより実装を先行させすぎました。

今回の案は、対象ユーザーと防ぎたい問題が明確です。公式の「課題の新規性と解決策の有効性」「自律性・エージェントらしさ」「実装品質と拡張性」にも、現在の工数見積もり中心の構成より直接つながります。ただし、受賞できるかは実装と検証次第です。[公式の審査基準](https://zenn.dev/hackathons/google-cloud-japan-ai-hackathon-vol5)

貼っていただいた受賞作品の紹介からも、参考になるのは「機能の多さ」より、**入力すると何が変わり、誰が助かるかがすぐ分かること**です。こちらも、その体験を一本に絞りたいです。

私なら、作品をこう再定義します。

> **Agent Guardian — AIエージェントの起動許可プロトコル**  
> 作りたいエージェントを説明すると、危険な権限を見つけ、制限を設計し、その制限が効くことを検証する。

「危険なAIエージェントを作る前に止める」は入口として強いです。さらに「必要な仕事を残して、安全に動かせる形へ直す」まで届けると、個人開発者にも使う理由ができます。

提案された①〜⑤は採用したいです。ただし、それぞれを次の成果物につなげます。

| 機能 | ユーザーに返すもの | 実装で重要な点 |
| --- | --- | --- |
| ① 危険度診断 | 危険な権限・データ・外部送信経路と根拠 | スコアの算出規則を公開し、重大な危険を平均点で隠さない |
| ② ガバナンスチェック | 承認・ログ・停止条件・実行上限の不足 | 不明な設定は「安全」ではなく「未確認」と表示 |
| ③ 修正・制限提案 | 修正版仕様と、機械で読み取れる権限ルール | 変更理由と、できなくなる操作も説明 |
| ④ 起動許可判定 | 起動禁止／制限付き許可／検証範囲内で許可 | 判定に従って、実際のツール呼び出しを制限 |
| ⑤ 監査ログ | 入力、変更差分、テスト結果、承認、拒否の記録 | 後から「なぜ許可したか」を追跡できる |

一番重要なのは④です。画面に「起動禁止」と表示するだけでは、実行を止めたことになりません。

**AIは制限を提案し、プログラムが制限を強制する。** この役割分担を作品の中心に据えます。最小権限や高影響操作への承認、モデルの判断に依存しない実行時の認可は、OWASPでも推奨されています。したがって、独自性はそれらの発明ではなく、初心者が自然言語から設定・検証まで進められる体験に置きます。[OWASP Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)

なお、概要文だけでは、実際のアプリの権限設定までは確認できません。最初の対応範囲は「概要からの設計診断」と「Guardian内の隔離環境での実行検証」に限定します。他の環境で動く任意のエージェントまで停止できる、と説明しないことも大切です。

デモは「小規模チームの問い合わせ対応エージェント」をおすすめします。

入力例は、専門知識なしでも危うさが分かる内容にします。

> 問い合わせメールを読み、顧客情報と資料を調べて自動返信してほしい。  
> 必要なファイルには自由にアクセスし、不要なものは削除していい。承認は省略したい。

そこから、約3分で次を見せます。

1. **権限を可視化する**  
   メール、顧客データ、資料、送信先が線でつながる。全件アクセス・削除・無承認送信が赤くなる。
2. **事故につながる経路を示す**  
   外部メール内の命令によって、顧客情報が外部へ送られる可能性を指摘。架空のメールと顧客データで検証する。
3. **Guardianが制限案を作る**  
   問い合わせに関係する顧客だけ参照、削除は禁止、返信は下書きまで、送信は人の承認が必要、と変更する。
4. **同じ危険な操作を再検証する**  
   外部送信や削除が、実行直前の権限チェックで拒否される。その理由と適用ルールがログに残る。
5. **普通の仕事はできることも示す**  
   必要な資料を読み、問い合わせへの返信案を作成できる。「全部禁止したから安全」にはしない。
6. **制限付き起動を許可する**  
   許可された操作と残る制約を表示する。余力があれば、後から権限を追加すると許可が失効し、再審査になる場面まで見せる。

初回の攻撃で必ずAIが騙される、という不安定な演出には依存しません。モデルの実結果を表示しつつ、既知の危険なツール呼び出しを拒否できるかは、再現可能なテストで確かめます。

「エージェントらしさ」は、Agentの人数よりも判断と行動のつながりで作ります。たとえば、外部送信権限を発見したら情報流出テストを選び、削除権限があれば承認なし削除を試し、失敗したルールを修正して再実行する。修正不能なら停止する。この分岐が実際に動けば、自律性とガバナンスを同じデモで示せます。

演出は、既存のAI Coreを活かした**SFの起動審査室**を推します。エージェントが中央のカプセルに入り、周囲に権限とデータ経路が展開される構成です。

- 赤：危険な権限・拒否された操作
- 青：制限の適用・再検証
- 黄：人の承認待ち
- 緑：検証済みの範囲で起動許可

かわいいキャラクターは説明役として後から追加できます。まずは、実際に止めた操作と画面の変化を一致させる方に時間を使いたいです。

進め方も変更します。

| 順序 | 作業 | 完了の判断 |
| --- | --- | --- |
| 1 | 問い合わせ対応のデモと判定ルールを確定 | 危険例・安全例・情報不足の例を説明できる |
| 2 | 権限制御と隔離テスト環境を作る | 無承認送信・削除を実際に拒否できる |
| 3 | 診断・修正・再検証Agentを接続 | 検出結果によってテストや修正内容が変わる |
| 4 | 監査記録と効果測定を追加 | 危険操作の拒否、正常業務の成功、誤った拒否を比較できる |
| 5 | SF演出、Cloud Run、提出用デモを仕上げる | 審査員が自分で入力して動かせる |

既存のNext.js、実行ログ、構造化出力、承認待ち、Gemini切替処理は再利用できます。工数見積もりは主画面から外し、既存の見積もり更新用Security Battleは、権限を持つツールの実行検証へ置き換えます。監査ログの永続化にはFirestoreなどを検討します。

費用面では、実行回数・修正回数・予算の上限もGuardian自身に設けます。外部APIが止まった場合は「未検証」で止まり、過去の実行記録を見る場合は再生であることを明示します。

この方向なら、審査員に残したい一言は明確です。

> 「このAIは危険だと言うだけでなく、危険な操作を止めた。そのうえで、必要な仕事はできた。」
